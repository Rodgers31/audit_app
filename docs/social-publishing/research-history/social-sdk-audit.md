# AuditGava: preliminary Social SDK audit

Research date: October 3, 2026. Read-only source/documentation review; no dependency installation, repository code execution, OAuth connection, credential access, or live publishing was performed. AuditGava application files, branches, processes, and browser sessions were not touched by this research.

## Recommendation

Social SDK is a promising **server-side adapter library**, with useful TypeScript contracts and explicit delivery outcomes. It can normalize much of Instagram, Threads, and TikTok publishing, but it cannot provide a complete direct integration across the four requested platforms: **there is no direct Facebook adapter**. Use an AuditGava-owned publishing interface and durable workflow, then choose native Facebook Graph API alongside selected SDK adapters, or a verified managed service. SDK declarations are implemented/mocked evidence, not proof that AuditGava has usable platform permissions. [Direct exports and runtime](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/package.json), [capability evidence](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/apps/docs/docs/reference/capabilities.mdx).

Two decisions need resolving before implementation:

1. **TikTok Direct Post eligibility:** TikTok's current guidelines expressly reject a private utility whose purpose is uploading to accounts managed by its own team. An AuditGava-only admin dashboard appears to fit that description. This is an inference about the proposed use case, grounded in the official rule; an SDK cannot remove the restriction. Public Direct Post also needs TikTok audit approval and creator preview/consent. Keep TikTok manual/export based initially, or confirm an approved managed provider's permitted use for this exact workflow. Do not assume selective automatic publishing will be allowed on TikTok. [TikTok Content Sharing Guidelines](https://developers.tiktok.com/docs/en/content-sharing-guidelines).
2. **Published package versus GitHub main:** npm latest is `0.5.0`, published September 24. Main includes a Postiz adapter added September 25, but the published `0.5.0` tarball has no `./cloud/postiz` export or files. A design based on the current docs could therefore reference an adapter unavailable in the current npm release. [Registry metadata](https://registry.npmjs.org/@opencoredev/social-sdk), [published release](https://github.com/opencoredev/social-sdk/releases/tag/%40opencoredev/social-sdk%400.5.0), [Postiz addition](https://github.com/opencoredev/social-sdk/commit/2042ce84f62803e06e62c92b48f92ae6da1d8af6).

### Facebook

The absence of `./facebook` in source and released exports is material. Including `facebook` in a platform union or managed capability matrix does not mean a direct Facebook adapter exists. The four managed source backends map Facebook account records and offer normalized publishing. [Package exports](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/package.json), [managed platform selection](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/cloud/common.ts#L40).

For native Facebook, publish as a Page with an app-authorized Page access token, not the logged-in browser cookie or a personal profile. Meta's collection discovers managed Pages and their tasks with `/me/accounts`, then uses the selected Page token. It also documents Facebook Reel initialization, upload and publication. Scope planning should start with `pages_show_list`, `pages_read_engagement`, `pages_manage_posts`; request Insights or webhook-management permissions only when required, and recheck the current Meta permission review for the chosen app/use case. This scope list is a planning target, not a verified AuditGava grant. [Meta Page token workflow](https://www.postman.com/meta/facebook/documentation/r56bjfd/facebook-api?entity=request-23987686-0b79260c-96bd-49de-875b-6076213785fc), [Meta Pages publishing documentation to validate](https://developers.facebook.com/docs/pages-api/posts/).

### Instagram

Requires a professional account. Meta supports businesses and creators; Stories publishing is limited to business accounts in the reviewed official collection. A Facebook Page link is required for **Facebook Login**, while **Instagram Login** does not require one. This is separate from configuring consumer Meta cross-sharing between the accounts. [Meta Facebook Login prerequisites](https://www.postman.com/meta/instagram/documentation/6yqw8pt/instagram-api?entity=request-23987686-6fa9ed1d-3310-4844-ad25-f0001ab66f11), [Meta Instagram Login](https://www.postman.com/meta/instagram/folder/6raa77c/instagram-api-with-instagram-login).

Direct SDK publishing uses Graph `v25.0`, which is hard-coded in this adapter, public HTTPS media, JPEG images, MP4/MOV video, caption max 2,200 code units and 1–10 attachments. It does not inspect codec, download bytes or create graphics. Normalize media in AuditGava before calling it. Multi-item carousels require known matching aspect ratios; this protects against implicit platform cropping. The normalized single-video route sets `media_type=REELS`; typed native methods also expose Stories and Reels. [Validation and dispatch](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/platforms/instagram.ts#L925), [Meta Reel container workflow](https://www.postman.com/meta/instagram/documentation/6yqw8pt/instagram-api?entity=request-23987686-fdf7020f-3cd0-4a5d-859b-66fb856b80b6).

Publishing scopes: Instagram Login `instagram_business_basic`, `instagram_business_content_publish`; Facebook Login `instagram_basic`, `instagram_content_publish`, `pages_read_engagement` plus Page discovery and eligible account tasks. Insights and comments need additional appropriate scopes. The server OAuth helper implements Instagram Login only; accepting a Facebook Login token in the publishing adapter does not implement Facebook OAuth or Page selection. [Adapter manifest](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/platforms/instagram.ts#L739), [OAuth configurations](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/server/oauth.ts#L70).

The SDK creates child and parent containers, records continuation IDs, checks asynchronous processing and reports `published` only when a native media ID is known. Its default workflow store is **in memory**. A production database-backed `InstagramWorkflowStore` with atomic claim/release is essential across worker restarts; using only `social_posts.status` would lose recovery context. No scheduler runs in the library; unpublished containers should not be created long before the intended publishing time. [Workflow contract](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/platforms/instagram.ts#L156), [processing/reconciliation](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/platforms/instagram.ts#L1110).

The SDK implements deletion with Facebook Login and declares `instagram_manage_contents` plus `instagram_basic`; it rejects deletion with Instagram Login. Confirm current availability/scopes in Meta and test actual account permissions before offering a rollback button. Post deletion and comment deletion are separate. Published media/captions are not editable through this direct adapter. [Deletion behavior](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/platforms/instagram.ts#L276), [deletion capability declarations](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/platforms/instagram.ts#L839).

### Threads

The SDK's direct route uses a separate Threads user ID and token, Graph version `v1.0` by default with configurable version, and `threads_basic`/`threads_content_publish`. An Instagram-linked Threads profile does not eliminate Threads app authorization. Meta's official collection shows the OAuth exchange followed by separate container creation and `threads_publish`. [OAuth configuration](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/server/oauth.ts#L94), [Meta Threads collection](https://www.postman.com/meta/threads/documentation/dht3nzz/threads-api).

Supports 500-character text, HTTPS images/video, up to ten carousel items, optional alt text, replies, quote/repost, own-post deletion and insights. Replies, deletion, insights, mentions and public search require their own permissions. Add only those used by AuditGava. The default workflow store is in memory and must be replaced with durable storage. There is no implicit polling or direct scheduling. Lost publish responses persist an ambiguous stage and are not replayed. [Workflow and options](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/platforms/threads.ts#L40), [manifest](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/platforms/threads.ts#L665), [prepare validation](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/platforms/threads.ts#L1181).

Meta exposes `/threads_publishing_limit` with publishing/reply quota fields. The inspected direct native interface does not expose this quota endpoint; add a small native API call if preflight quota checks are needed. Use the returned quota configuration instead of hard-coding a remembered daily cap. [Official quota endpoint](https://www.postman.com/meta/threads/request/w3x0n4g/retrieve-publishing-quota-limit), [SDK native interface](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/platforms/threads.ts#L128).

### TikTok

Actual source uses Content Posting API v2 and only verified-origin `PULL_FROM_URL`, not local upload. Supports one video or 1–35 photos. Video caption max 2,200 UTF-16 units; photo description max 4,000 and title max 90. JPEG/WebP photos and MP4/MOV/WebM videos are accepted MIME types. The adapter requires known video duration and compares it against current creator privileges. Media URLs must have owned/verified origins, remain reachable during download, and avoid redirects. [SDK validation](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/platforms/tiktok.ts#L184), [TikTok media transfer](https://developers.tiktok.com/docs/en/content-posting-api-media-transfer-guide), [TikTok photo API](https://developers.tiktok.com/docs/en/content-posting-api-reference-photo-post).

Per-post options explicitly require consent, privacy, comments/duet/stitch choices, commercial disclosure, AI-generation choice and draft/direct choice. The current published docs' examples omit `aiGenerated` and `draft`, which actual source requires as booleans. AuditGava must render fresh creator information and actual user choices; setting `consentGiven: true` in an unattended worker is not equivalent to obtaining consent. The adapter re-queries creator information at dispatch to check changed privacy/duration and video interactions. [Source requirements](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/platforms/tiktok.ts#L200), [dispatch checks](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/platforms/tiktok.ts#L560), [official creator UX](https://developers.tiktok.com/docs/en/content-sharing-guidelines).

Direct Post uses `video.publish`; inbox/draft upload uses `video.upload` and requires the creator to complete publishing in TikTok. Initial API acceptance is not publication. The SDK retains `publish_id`, maps processing/failure/inbox states, and requires exactly one usable native public ID before returning `published`. `PUBLISH_COMPLETE` without a public ID stays `accepted`, including private posts. A poller must use a terminal private/inbox policy rather than poll forever. Video Display API metrics require `video.list`, account counters `user.info.stats`. Photo analytics are not demonstrated by the SDK's video-query route. [Outcome handling](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/platforms/tiktok.ts#L686), [metrics](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/platforms/tiktok.ts#L774), [official status API](https://developers.tiktok.com/docs/en/content-posting-api-reference-get-video-status).

Official current limits include six initialize requests per minute per user token, twenty creator-info requests per minute and thirty status requests per minute. Daily creator caps and moderation can apply even after successful API acceptance. An unaudited Direct Post app is private-only and limited to five publishing users per day; approval is a prerequisite for public production posting. The internal-tool exclusion is particularly consequential for AuditGava. [Direct Post](https://developers.tiktok.com/docs/en/content-posting-api-reference-direct-post), [creator info](https://developers.tiktok.com/doc/content-posting-api-reference-query-creator-info), [status limits](https://developers.tiktok.com/docs/en/content-posting-api-reference-get-video-status), [audit and intended-use rules](https://developers.tiktok.com/docs/en/content-sharing-guidelines).

Native gaps include `FILE_UPLOAD`, upstream token revocation, and TikTok's best-effort `/v2/post/publish/cancel/` for an ongoing URL download. That cancellation is **not deletion of a published video** and cannot be relied on after processing has started. No inspected SDK TikTok method implements cancellation or published deletion. An emergency switch can stop new AuditGava work, but cannot promise removal of already-published TikTok content. [Official cancellation](https://developers.tiktok.com/docs/en/content-posting-api-media-transfer-guide), [official revocation](https://developers.tiktok.com/docs/en/oauth-user-access-token-management), [SDK native surface](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/platforms/tiktok.ts).

## Authentication, refresh and security model

The SDK server package supplies OAuth providers, `ConnectionManager`, account discovery and exact callback/state binding. X uses S256 PKCE. The inspected TikTok web and Meta flows use confidential-client authorization-code exchange without adding unsupported PKCE parameters. Attempts and tokens still need AuditGava-owned persistent stores and authenticated admin authorization. A profile handle is display information; authorization must use stable platform/account ID and backend route. [OAuth implementation](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/server/oauth.ts), [ConnectionManager](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/server/connections.ts), [connection guidance](https://social-sdk.dev/docs/authentication).

Threads/Instagram Login helpers exchange short-lived tokens for long-lived tokens and refresh via their platform-specific access-token refresh endpoints. TikTok refresh uses its refresh token; newly rotated tokens must replace old tokens atomically. Official TikTok documentation states 24-hour access tokens and initial 365-day refresh tokens; SDK `OAuthTokenSet` records access expiry but **does not retain `refresh_expires_in`**, so track refresh expiry in the app if required. Facebook Login/Page token lifecycle needs native work because this SDK has no Facebook provider. [Refresh source](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/server/oauth.ts#L806), [token parsing](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/server/oauth.ts#L288), [TikTok token management](https://developers.tiktok.com/docs/en/oauth-user-access-token-management).

`CredentialManager` supports compare-and-set revision and a refresh lock, but its supplied implementations are memory stores; it does **not** encrypt tokens or manage KMS secrets. Use database ciphertext with authenticated encryption/envelope keys, server secret management, durable distributed locks with fencing, token revision checks, explicit reconnect states and revocation handling. A refresh worker must schedule refresh before expiry and avoid replaying an uncertain rotation. [Credential code](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/server/credentials.ts).

Only an authenticated backend should load credentials and construct clients. The browser sends an app-owned connection ID and draft revision, never tokens, an arbitrary platform ID, provider API keys or native client options. Verify admin/account authorization again at dispatch. `social.native(..., { acknowledgeUnsafe: true })` bypasses normalized client authorization/concurrency middleware and needs its own controlled backend wrapper. [Security guidance](https://social-sdk.dev/docs/reference/security).

## Publishing, idempotency, errors and rate limits

The client validates all targets before network dispatch, routes each selected account explicitly and returns independent target outcomes. Accepted, scheduled, processing, published, failed, cancelled, not-submitted and unknown mean different things. A mixed success is not atomic: Facebook can succeed while Instagram fails. AuditGava needs one delivery row per platform plus historical attempts; successful destinations must remain untouched on retry. [Client publishing](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/core/client.ts#L804), [public outcome types](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/core/types.ts).

There are important limits in the current idempotency code:

- An `idempotencyKey` with no configured `idempotencyStore` supplies routing/provider keys but does not create durable client-side duplicate protection.
- The fingerprint includes the **entire target list**, content, options and schedule. Reusing one multi-target key with a failed-target subset conflicts. Reusing the identical request returns saved outcomes, including saved failures, rather than redispatching.
- A claimed target with no saved result returns `unknown`; automatic replay would be unsafe.
- Failure to save an outcome in the SDK store is swallowed and the in-memory result is returned. AuditGava must observe and commit its own delivery/attempt records before declaring durable completion.

These source behaviors qualify the docs' more optimistic failed-target retry narrative. Prefer independently claimed destination intents and an explicit attempt identity only after reconciliation confirms that reattempting cannot duplicate a public post. Keep immutable approved revision/hash and unique `(post_revision, connection, intent)` in the database. Implement recovery around the actual pinned version and test crashes and concurrent attempts. [Idempotency implementation](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/core/client.ts#L817), [existing-claim handling](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/core/client.ts#L866), [save failure behavior](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/core/client.ts#L944).

HTTP reads may retry within a maximum five-attempt/elapsed-time budget, using Retry-After or X reset headers plus exponential jitter. Mutations get one transport attempt; lost responses or server errors after dispatch become ambiguous rather than blind replay. Structured `SocialError` supplies permission, reconnect, approval, rate-limit, billing, media and uncertain-write outcomes with retry disposition. Some mappings are conservative: a 429 without usable retry headers can carry `never`. Application policy must distinguish a confirmed rejection from unknown acceptance, and not blindly interpret every failed result as retryable. [HTTP transport](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/transport/http.ts#L224), [managed error mapping](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/cloud/common.ts#L112), [error reference](https://social-sdk.dev/docs/reference/errors).

SDK concurrency bounds are per client/backend instance, not a distributed rate limiter or posting-frequency policy. Use durable jobs, per-account locks, platform budgets, daily/hourly post caps, fair backoff and a dead-letter/reconnect queue. Persist all asynchronous media container/upload/publish IDs. Instagram exposes a native publishing-limit read; Threads needs a small native quota query. Meta usage-header handling, true live quotas and SDK hard media limits should be rechecked before rollout. [Concurrency](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/core/concurrency.ts), [Instagram limit helper](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/platforms/instagram.ts#L1587), [Threads quota](https://www.postman.com/meta/threads/request/w3x0n4g/retrieve-publishing-quota-limit).

## Webhooks and event handling

Direct Instagram and Threads verify untouched raw bodies using Meta HMAC-SHA256; TikTok verifies its signature including timestamp, with a configurable default 300-second window. Server helpers answer Meta GET challenges and decode provider events. SDK has no webhook hosting or subscription management. Meta signatures lack a signed timestamp, so durable event/body deduplication matters. Unknown event types are preserved; Threads mentions/publish are not mapped to a full normalized completion event. Match delivery IDs and confirm final state with native reads where necessary. [Verification/decoding source](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/server/webhooks.ts), [event mapping guidance](https://social-sdk.dev/docs/events).

Use an authenticated webhook inbox transaction: raw signature verification, size bounds, stable dedup key, account-ID resolution through stored connections, then asynchronous processing. Never trust a tenant or admin identity in a webhook body. Quarantine unverifiable/unknown-account events, enforce monotonic terminal delivery updates, and allow bounded replay. TikTok `publish_id` is useful for correlation; a webhook arrival alone is not a successful public post. PostFast has no webhooks; Postiz's unsigned success hooks are rejected by the SDK, so both need durable bounded status polling. [Inbox implementation](https://github.com/opencoredev/social-sdk/blob/a76fb612c8abd5926fbfa40c9a3f556a523531ea/packages/social-sdk/src/server/webhooks.ts), [official TikTok outcome events](https://developers.tiktok.com/docs/en/content-posting-api-reference-get-video-status).

## Implementation sequence informed by this audit

1. Resolve TikTok eligibility/provider strategy, native Facebook versus managed delivery, Meta app/account class and exact scopes. Do this before promising full cross-platform automation.
2. Implement encrypted account connections, token lifecycle, stable account IDs, admin authorization, disconnect/revocation handling, durable workflow/idempotency stores and observability. Keep social credentials backend only.
3. Add an AuditGava `PublisherAdapter` contract with `prepare`, `publish`, `getDelivery`, `getMetrics` and capability-gated `remove`; normalize native Facebook and any SDK route behind it. Do not expose a universal rollback promise.
4. Prove one human-approved post per initial platform with controlled live accounts and appropriate content, then media, expiry, processing, missing scopes, quotas, webhook replay and crash recovery. Keep TikTok manual/export or permitted managed delivery until eligibility is established.
5. Add the durable review/scheduling queue and only then generate platform variants from validated source events. Reapproval should bind to edited revision, asset checksum, numeric facts and target configuration.
6. Run auto-approval policies in shadow mode first, then enable tightly scoped deterministic data-release announcements with source/freshness gates, duplicate prevention, per-platform limits and emergency pause. Exclude sensitive audit allegations and TikTok unless the specific permission/consent model permits them.

No integration was implemented in this round. Future live feasibility remains conditional on AuditGava's developer applications, granted scopes, account eligibility, provider approvals and successful controlled platform verification.
