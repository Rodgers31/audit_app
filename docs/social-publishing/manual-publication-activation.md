# Manual publication: preparation and activation

The intended workflow is **add media → review the saved caption, source and each destination preview → Publish now → inspect each destination's delivery result**. Manual authorization does not require enabling automatic generation, approval, scheduling or publishing. A queued command is not confirmation that a platform published it.

Two previously missing operator steps are explicit. For a connected Meta account, **Verify existing publishing access** checks the saved grant against the exact provider identity, permissions and content tasks, then persists the verified native capability proof while account publishing stays paused. It does not exchange a new OAuth code or enlarge the grant. The administrator can then separately enable or pause that destination through an authenticated, audited command. These commands use the existing global controls version and a current account/credential state token; stale requests refuse and ambiguous responses retain the original command body and idempotency key. They do not change the global publishing value or start a worker. Pausing does not erase an unresolved delivery, release its ownership or establish that an in-flight request stopped.

Retained privacy requests also remain authoritative after verification. Account consent reads current ownership and receipt metadata without decrypting credentials: a matching request blocks enabling, and ambiguous ownership or an incomplete bounded inventory reports unavailable. Known unrelated subjects and foreign app namespaces do not inherit another grant's hold. The final command witness checks this state again before commit. Pause remains available for these holds; a missing privacy relation is a schema failure rather than an empty-history result, and the separate global pause remains available.

## Current production position

The read-only 2 November 2026 UTC observation at deployed source `9bbdde51d6ebe9e38bf0aa86f4d0f086c5cdffeb` found Facebook Pages and Instagram Graph via Facebook Login connected. Both account publishing values and global publishing/generation/automation values were false; no social worker process was running. There were no connected Threads, X or TikTok rows in that complete bounded inventory. Public profile links and local sample accounts do not establish connections.

Both saved Meta capability snapshots had `adapter_available=false`, no supported formats and publishing marked unsupported. They were connected without native publishing proof. Registering an adapter or enabling account consent cannot silently upgrade those snapshots; the explicit provider-backed verification step addresses that gap. It still requires accepted native server configuration, a usable saved grant and no conflicting delivery ownership. Reconnect only when the saved grant or exact identity/permissions cannot be verified.

For both accounts, the stored Page-credential metadata had no scheduled access expiry, no recorded revocation and data-access expiry on 16 January 2027. These are stored metadata observations, not new provider permission or token-validity checks or an inventory of distinct credentials. Parent User access expiry remains distinct from derived Page access expiry; Page access expiry, both data-access expiries, revocation, identity and unresolved refresh checks still apply.

Production publishing, uploads, workers and financial generation remain off. No provider send, media upload, reconnection, worker start or account-control mutation is part of this implementation's acceptance.

A separate configuration-presence read found existing social R2 settings, media credential settings, an inspector path, a named restricted-worker role and worker DSN settings. It exported no secret values. The explicit worker shutdown deadline was unset. Presence alone does not establish working storage, effective SQL privileges, inspector execution, accepted shutdown timing or sufficient capacity; this evidence does not justify creating another service or enabling the launcher.

The existing deployed `social.worker.role_admin --verify` command subsequently succeeded for `audit_social_worker` using the named worker DSN. This was a bounded read-only authority check; it changed no role or grant and started no worker. It establishes that role contract at that observation, not host capacity, secret custody, media restore or provider delivery.

## What the operator must distinguish

| Boundary | Required preparation and evidence |
| --- | --- |
| Account consent | Review the exact connected identity and reported blockers. Verify existing Meta access where its native proof is missing, then use the separate account publishing control for that destination; do not patch database rows directly. Verification and consent leave global and per-platform controls authoritative. Neither command certifies a live worker or successful post. |
| Native delivery | The API and worker need the existing explicit native configuration and accepted operational gates. `SOCIAL_NATIVE_ENABLED` and `SOCIAL_NATIVE_OPERATIONAL_GATES_VERIFIED` are default-off ceilings, not substitutes for evidence. Existing usable Page maintenance must not require a new OAuth callback; a new connection/reconnection still needs its own callback privacy acceptance. |
| Upload and media reads | `SOCIAL_MEDIA_ENABLED` controls upload issuance. Existing worker-only private reads use `SOCIAL_WORKER_MEDIA_READS_ENABLED` and the existing private R2 configuration. The current native worker contract requires that read configuration even for text-only work; this release does not introduce a media-free bypass. Accept actual application-media storage, exact origin/CORS, inspection, quota, backup/independent restore and retention ownership before enabling uploads. Source-evidence buckets and synthetic diagnostics are not application-media acceptance. |
| Worker | Use the existing restricted worker login and role verification, global ownership and [supervision contract](../../backend/social/worker/SUPERVISION.md). The existing-container launcher is controlled by `SOCIAL_WORKER_SUPERVISOR_ENABLED`; it starts no social child while off. Keep the explicit worker DSN/role and shutdown settings private. The implementation adds no service or new hosting plan. Intended-host capacity, reserve and shutdown acceptance remain required; a test container cannot establish them. |
| Draft and destination | Existing drafts can be manually reviewed without enabling financial generation. Refresh/validate the exact saved revision and every selected destination, including source holds, account format/media requirements, accessibility and required factual attestation. An enabled account never overrides an evidence hold or permits editing an already-dispatched payload. |
| Delivery and recovery | Require current worker evidence, then inspect each target's confirmed result and public remote URL. A queued result, missing response or generic status lookup is not a published result. Reconcile uncertain attempts using the existing recovery commands; do not create a new-key resend or clear an account hold merely because a lease expired. |

## Separate, bounded launch decision

After applicable evidence is accepted, the owner can authorize a bounded cutover for named connected accounts and reviewed test content. That decision must specify which controls may change, the actual media/profile and provider checks, the operating budget and stop/rollback observations. It is not implied by merging this code or by the existence of an enable button.

Keep financial generation and automatic approval/scheduling/publishing off during a manual-only launch. Enable only the accepted storage/read/native/worker layers and the explicitly selected account/global consent needed for that launch. No paid API tier, new platform connection, additional resource or broader grant follows from this document.

For rollback, pause global and affected account publishing first. Stop new worker admission, positively drain/reap the owned process and retain its closure/ownership evidence. Preserve uncertain targets and the additive schema/history. Restore the previous reviewed application version only under the existing [worker rollback procedure](../../backend/social/worker/SUPERVISION.md#manual-handoff-and-rollback); elapsed time is not a safe-release proof. Disable uploads independently. Do not automatically restart or release a sticky owner after an uncertain shutdown.

The remaining launch decisions are tracked in [the release gate ledger](../releases/admin-publish-workflow-20261101/LAUNCH_GATES.md). Local synthetic API, browser, PostgreSQL and native-adapter tests establish code behavior within their recorded scopes; they cannot supply missing provider, independent custody, production media or representative operating evidence while those operations remain off.
