## Official product sources

Read directly in existing Chrome on 18 October 2026; web retrieval of the first two URLs was unavailable/429, so no secondary article is used as authority.

- [Facebook Reels Publishing](https://developers.facebook.com/documentation/video-api/guides/reels-publishing), updated 30 July 2026: Page identity and permissions; start -> numeric video ID/upload URL; canonical rupload binary request using `offset` and total `file_size`; `GET /video-id?fields=status`; finish with `video_state=PUBLISHED`. Interrupted Facebook uploads expose `uploading_phase.bytes_transfered` (one r in transferred). Offset must be read before resuming. The finish acknowledgement is a success boolean, not a final public post identity. Facebook enforces 30 Reels/24h; provider rate-limit rejection remains authoritative.
- [Instagram Content Publishing](https://developers.facebook.com/documentation/instagram-platform/content-publishing), updated 30 June 2026: Facebook Login Page token; `media_type=REELS` plus `video_url`; poll `status_code`, require `FINISHED` before publishing; final media ID from `media_publish`; quota check before creation and publication. `PUBLISHED` container state without final media ID is insufficient to recover an unknown publication. Five one-minute status checks are recommended.
- [Instagram User Media](https://developers.facebook.com/documentation/instagram-platform/instagram-graph-api/reference/ig-user/media), updated 28 September 2026: MP4/MOV, H264/HEVC, 23–60fps, 3s–15min, 300MB ceiling; Reels return `media_type=VIDEO`, `media_product_type=REELS`. Caption limit2200, hashtags30, mentions20. `alt_text` only supports images. A container response does not prove upload success. Account privacy settings apply at publication.
- [Instagram resumable uploads](https://developers.facebook.com/documentation/instagram-platform/content-publishing/resumable-uploads), updated 15 March 2026: binary resumable upload requires Facebook Login for Business. The existing generic Facebook Login capability does not establish that prerequisite, so this slice uses the supported version-bound retained fetch URL. No binary IG product or permission is invented.

## Bounded media and proof decisions

DEC-723-1: Initial application intersection is one ready, inspected MP4, 15–45 seconds, 9:16, width540–1080, 24–60fps, at most50,000,000 bytes. These are deliberately narrower application limits, not invented platform ceilings. Existing inspection requires decoded H264 and optional AAC; Studio emits720x1280/24fps H264. Bytes/hash/metadata enter immutable approval. Final worker admission recomputes the approved resolved payload, and the payload-scoped retained-media port verifies object identity, bytes and SHA256. Facebook uploads exact bytes. Instagram signs only its exact retained object, validated origin/path/version/hash and expiry; expired or changed access never triggers a new container blindly.

DEC-723-2: Upload success, readiness, publication acceptance and confirmed public visibility are distinct. Official status/owner media reads do not establish unrestricted public accessibility. The adapter retains numeric refs and remains Processing then held/unknown after bounded checks. The completed original-scope human authority is [Meta Reels record-existing](../META_REELS_PUBLIC_OUTCOME.md): two distinct administrators, independent retained anonymous-public and owner-identity capture packets, exact approved video/caption/product binding, current version/lease/dispatch/duplicate checks and atomic audited settlement. Production capabilities expose bounded Reels with `reel_operator_confirmation=supported`, `reel_public_confirmation=requires_review` and `reel_automatic_confirmation=unsupported`. Actual dispatch still requires existing server/config/account approval and remains off in this task. Full worker tests now use the real native registration rather than test-only capability overrides. No authenticated owner permalink, guessed field, feed absence, or provider boolean is automatic public confirmation. The human authority validates workflow/binding, not off-system pixels or honesty; collusion by two administrators is outside that explicitly documented trust model. Actual operator custody/provider access and acceptance remain separate.

DEC-723-3: Each external operation has a durable intent before transport. Unknown session creation cannot be replayed. A partial Facebook upload resumes only its original numeric session at a freshly verified monotonically bounded offset, with the same approved bytes. No redirects, provider-selected host, hosted Facebook upload, automatic wire retry or new session fallback exists. At most five saved upload attempts and bounded status checks; worker deadlines remain authoritative. Lost publication receipts never authorize another finish/publish.

DEC-723-4: A nonpublic upload can retain an account hold after a crash even when its session is authoritatively recovered. A typed optional continuation proof binds original operation UUID/request fingerprint, account, approved payload and output checkpoint hash. The durable repository independently checks latest mutating intent, absence of a public dispatch permit, allowed nonpublic operation and successful result before clearing only that target's hold. This proof is not an absence proof and cannot clear ambiguous publication. All pre-existing reconciliation paths remain held unless they supply this new exact proof or their existing accepted proof.

No migration, credentials, grants, new flag, paid service, hosted CI, preview deployment or production action is part of this code change. Live publishing/uploads/native processing/supervision remain outside this task's execution authority.
