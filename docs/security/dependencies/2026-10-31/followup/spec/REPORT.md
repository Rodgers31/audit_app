**Specific minimatch applicability.** My assessment is that the `firstPhasePreProcess`/`secondPhasePreProcess` amplification mechanism described by GHSA-g3hv-75wg-m249 is absent from the exact installed legacy 3.1.5 implementation. The [maintainer advisory](https://github.com/isaacs/minimatch/security/advisories/GHSA-g3hv-75wg-m249) describes 10.2.6, while the [aggregate advisory](https://github.com/advisories/GHSA-g3hv-75wg-m249) assigns `<11.0.1`. That discrepancy remains unresolved upstream; this review does not amend or dismiss the published range. The [fix](https://github.com/isaacs/minimatch/commit/77a0f5c) caps generated alternatives and skips pairwise deduplication above 1,000 alternatives. The installed 3.1.5 parser lacks those phases, whereas the published 7.x implementation introduced the optimization family. The [upstream changelog](https://github.com/isaacs/minimatch/blob/77a0f5c/changelog.md) records preprocessing in 7.0 and the optimizationLevel option/default change in 7.1.

The exact upstream pattern, reduced to eight repetitions, is `Array(8).fill('**/../a/b').join('/')`; options are `{ optimizationLevel: 2, braceExpandMax: 8 }`. Fifty isolated registry-version children were run, with a 96 MB V8 heap, three-second CPU limit and four-second wall limit per child. All completed normally. Instrumented phase counts and separate uninstrumented runs agree on final cardinality. [version-matrix.json](runs/version-matrix.json) records every command, hash, phase observation and result.

Levels 0 and 1 were also executed. Version 7.0 runs the new preprocessing regardless of the later option; 7.1+ uses the advanced phase at level 2. Legacy 3.1.5 ignores these newer options and stays at one alternative. Uninstrumented n=4/6/10 controls produce 16/64/1,024 alternatives on 10.2.6, eight on 11.0.3 with this limit, and one on 3.1.5. This is finite, mechanism-specific evidence, not an asymptotic proof for all possible patterns. The actual root 3.1.5 entry and installed TypeScript caller's 11.0.3 entry are byte-identical to their independent registry fixtures. All six modern lock locations are already 11.0.3 and the sole legacy location is development-only 3.1.5.

Both cases passed; the comment explicitly excludes general ReDoS clearance.

**A concrete residual performance limit.** An independent matching control unrelated to the optimizer uses `'*a'.repeat(12)+'b'` against 32 `a` characters. In two runs the legacy 3.1.5 child reached matching and exceeded the 750 ms wall bound; it was killed. The same input returns false promptly on 11.0.3, while n=4 and n=8 complete on both. The [bounded controls](runs/other-pattern.json) use a 64 MB heap and one-second CPU bound. This is an observed backtracking cost, not a newly attributed CVE, proof of an infinite hang, or proof of online exploitability. It confirms that the absence of this advisory's preprocessing mechanism must not become a claim that legacy minimatch is free of denial of service. The [legacy README](https://github.com/isaacs/minimatch/blob/v3.1.5/README.md) also warns about untrusted patterns.

**Corrected modern regression.** The actual candidate test was executed with only the TypeScript caller's minimatch load redirected to isolated 10.2.6. It fails specifically on `256 !== 8`; the hook confirms the actual caller was intercepted. The same permanent test passes against installed 11.0.3. The [RED receipt](runs/exact-permanent-minimatch-red.receipt.json) has expected exit 1 and requires the named assertion and interception, rather than treating any command failure as RED. The prior pattern generated intermediate alternatives but deduplicated down to the asserted ceiling; it was not a valid amplification regression. No claim of absent intermediate splitting remains in the final test comment or reviewed documentation.
