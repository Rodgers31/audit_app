## Reproductions, fixes and verification

- **Key refresh:** four unverified key IDs caused five mocked upstream fetches; concurrent cold valid requests caused four. A process-local lock and monotonic30s attempt budget now share cold, unknown-key and failed-provider refreshes. Known valid keys retain their1h TTL; expired keys fail closed. New key rotation can wait up to30s. Invalid algorithms/key IDs and >16KiB tokens refuse before key I/O; malformed key documents refuse without disclosing provider errors. Both current-user entry paths call the shared decoder.
- **Limiter storage:** at a test cap3, a fourth new identity was admitted before the fix. Both the default in-memory middleware and Redis's fallback now use the same expiry-ordered admission helper, capped at10,000 live identities and at the configured number of timestamps per identity. A full map refuses new identities without evicting live budgets; expired clients release capacity. Raw forwarded headers do not select identity. Existing loopback/unknown exemptions and upstream proxy-trust configuration were not changed or deployment-certified.
- **Callback:** the original handler could form an external authority after an otherwise successful code exchange. Only validated root-relative app paths now follow an exchange. Recovery still renames the code, selectively clears session-cookie chunks and avoids exchange. Every redirect is private/no-store and no-referrer; user-controlled callback log text was removed.
- **Auth schema:** original bootstrap policies allowed changing/inserting privileged profile roles and reading subscriber records in a two-user PostgreSQL replay. The forward SQL uses an invoker trigger to protect role writes by anon/authenticated and a restrictive subscriber policy that remains effective alongside old permissive policies. No grants/credentials change. Service-role/owner operations and ordinary profile edits remain valid. Trigger covers INSERT/UPDATE, including upsert; subscriber policy covers row-level SELECT/INSERT/UPDATE/DELETE access. Table-wide privileges such as TRUNCATE/REFERENCES are not constrained by RLS and are not changed or certified here. **Apply only after separate auth-project review/approval; backend Alembic may target a different project.** #789 owns hosted verification.
- **Scope controls:** actual two-user watchlist/alert HTTP reads, delete, patch and read-all preserve ownership and no-store responses. The signed provider event callback was a stale route-scanner exception, not a new auth bypass. Its exception now requires mounted HTTP controls for both providers: missing/bad signatures refuse before persistence, and disabled configuration remains503.
